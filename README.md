# Calibre Sync (modernized)

Android app that turns your phone/tablet into a Calibre "wireless device" (Smart Device App
protocol) plus a basic OPDS/Content Server browser. This is a 2024/2025-era Gradle
modernization of the original 2013 `net.sengjea.calibre` project (Eclipse ADT, AGP 0.7,
`minSdk 5`).

## What changed vs. the 2013 original — short version

- Rebuilt as a standard Android Studio / Gradle project (`settings.gradle.kts`,
  `app/build.gradle.kts`, AGP + Gradle 8.x, JDK 17, Kotlin DSL).
- `minSdk 24` (Android 7.0) / `targetSdk 35` — check `app/build.gradle.kts` and bump
  `compileSdk`/`targetSdk` if a newer stable API level exists by the time you build.
- AndroidX throughout (`android.support.*` → `androidx.*`), `android.preference.*` →
  AndroidX Preference (`SettingsActivity` rewritten as `AppCompatActivity` +
  `PreferenceFragmentCompat`).
- The old `android.lib.BarTab*` ActionBar/TabHost tab library (which no longer compiles —
  `ActionBar.newTab()` was removed) was **reimplemented from scratch with the same public API**
  (`BarTab`, `BarTabManager`, `BarTabActivity` — same class/method names), now backed by a
  Material `TabLayout` instead of `TabHost`/`ActionBar.Tab`. This means `MainActivity.java`
  and the fragments (`ConnectionFragment`, `CollectionFragment`, `OPDSBrowserFragment`) needed
  **no changes** for the tab framework itself.
- `CalibreService` is now a **foreground service** with a low-importance notification channel
  (`foregroundServiceType="dataSync"`), required since Android 8+ kills plain background
  services that hold a long-lived socket.
- The old manifest-registered `ServiceReceiver` (static `<receiver>` for the implicit
  `android.net.wifi.STATE_CHANGE` broadcast — restricted since Android 7/8) was removed and
  replaced with a `ConnectivityManager.NetworkCallback` registered dynamically inside
  `CalibreService`.
- `Uri.fromFile()` (crashes with `FileUriExposedException` from API 24+ when handed to another
  app via an `Intent`) replaced with `FileProvider` `content://` Uris, both for the "book
  received" notification tap-to-open and for `OpenBookActivity`. See
  `res/xml/file_paths.xml` and the `<provider>` entry in the manifest.
- `NotificationCompat.Builder(context)` (deprecated no-channel constructor) → channel-aware
  constructor + `NotificationChannel` created in `onCreate()`.
- Added the two Smart Device App opcodes the 2013 client didn't know about:
  `SET_LIBRARY_INFO = 19` (acknowledged with `OP_OK`, library name stored) and
  `ERROR = 20` (logged and surfaced via the existing error-broadcast mechanism instead of
  being silently dropped).
- `ConnectionInfo` no longer hard-codes `http` for the Content Server URL — it now honors
  `https://` if you enter a Content Server URL configured with `--ssl-certfile` on the Calibre
  side. (The wireless-device TCP socket itself is unaffected either way — Calibre doesn't use
  TLS there.)
- `android:usesCleartextTraffic`/`network_security_config.xml` added, since Android 9+ blocks
  plain HTTP by default for `targetSdk 28+` apps, and this is a LAN-only app by design.
- **Storage: user-choosable book folder.** Settings > Book Folder now opens the system's
  `ACTION_OPEN_DOCUMENT_TREE` picker so you can choose any folder on the device's internal
  storage or SD card, instead of being confined to the app-specific external files directory.
  This needs the `MANAGE_EXTERNAL_STORAGE` ("All files access") permission on Android 11+, or
  the classic `WRITE_EXTERNAL_STORAGE`/`READ_EXTERNAL_STORAGE` runtime permissions below that —
  see "Known issues" below for the trade-offs of this approach vs. a full SAF/`DocumentFile`
  rewrite.

Full opcode/API-level detail is in `CHANGELOG_MIGRATION.md`.

## How to build

```bash
# from the project root, after gradlew exists (see above)
./gradlew assembleDebug
```

Output: `app/build/outputs/apk/debug/app-debug.apk`

Debug builds sign automatically with Android's built-in debug keystore — no setup needed.

For a **release** build, copy `keystore.properties.example` → `keystore.properties`, fill in
your own keystore (generate one with `keytool -genkey ...`, see the comments in that file),
then:

```bash
./gradlew assembleRelease
```

Never commit `keystore.properties` or a real `.keystore`/`.jks` file (already in
`.gitignore`).

## Testing the Calibre connection

1. Install the APK on a phone/tablet on the **same Wi-Fi network** as your computer.
2. In Calibre desktop: **Connect/share → Start wireless device connection** (or the
   "Connect to folder"/Smart Device menu, depending on your Calibre version).
3. Open the app — it broadcasts UDP `"hello calibre"` on ports `54982, 48123, 39001, 44044,
   59678` and should discover the server within a few seconds. If not:
   - Confirm both devices are on the same LAN/subnet (some routers isolate Wi-Fi clients from
     each other — "AP/client isolation" — which breaks discovery).
   - Check your computer's firewall isn't blocking the ports above or Calibre itself.
   - Try the manual connection dialog (enter the wireless-device host:port shown in Calibre's
     "Start wireless device connection" dialog) if UDP broadcast discovery doesn't work on your
     network.
4. Send a book from Calibre to the device, and try uploading a book from the device's
   Collection tab back into Calibre.
5. Browse the OPDS tab, which talks to Calibre's Content Server (enable it in Calibre's
   sharing preferences if it's off).

## TTS Models / NghiTTS setup ("Đọc cho nghe")

The in-app reader's "Đọc cho nghe" (TTS) feature has three engines, one plugin class each under
`net.mrphan.calibre.reader.tts` (`TtsEngine` interface, registered in `TtsEngineRegistry`):

- **System TTS** (`SystemTtsEngine`) — wraps `android.speech.tts.TextToSpeech`, whatever voices
  are already installed on the device. Works out of the box, no setup.
- **Edge TTS** (`EdgeTtsEngine`) — cloud voices from Microsoft Edge's unofficial "Read Aloud"
  service (same reverse-engineered WebSocket protocol as `rany2/edge-tts`/Readest). Works out of
  the box too (just needs Internet) — no API key, nothing to download. It's an **unofficial**
  API, so it can break if Microsoft changes the protocol; if it stops working, sentences are
  silently skipped rather than crashing the app.
- **NghiTTS** (`NghiTtsEngine`) — offline Piper/VITS voices (from
  [nghimestudio/nghitts](https://github.com/nghimestudio/nghitts) or any Piper voice on
  [rhasspy/piper-voices](https://huggingface.co/rhasspy/piper-voices)) run locally via
  [k2-fsa/sherpa-onnx](https://github.com/k2-fsa/sherpa-onnx). This one needs two one-time setup
  steps before it compiles/works — see below.

### 1. Download the sherpa-onnx Android `.aar`

sherpa-onnx isn't published to Maven Central, so it's added as a local file dependency
(`app/build.gradle.kts`: `implementation(files("libs/sherpa-onnx.aar"))`).

1. Go to <https://github.com/k2-fsa/sherpa-onnx/releases>, find the latest TTS-capable Android
   release, download `sherpa-onnx-vX.Y.Z-android.tar.bz2`.
2. Extract it to get `sherpa-onnx-*.aar` (you generally only need `armeabi-v7a` + `arm64-v8a` —
   drop `x86`/`x86_64` unless you need to run on an Intel emulator, to keep the APK smaller).
3. Copy/rename it to `app/libs/sherpa-onnx.aar` (see `app/libs/README.md`).

**Important:** the exact Kotlin API surface of `com.k2fsa.sherpa.onnx.OfflineTts*` used in
`NghiTtsEngine.kt` was written against the API documented at
<https://k2-fsa.github.io/sherpa/onnx/kotlin-api/index.html> at the time this was implemented —
that surface has drifted across releases before. This sandbox has no Android SDK to compile
against, so **after adding the real `.aar`, run `./gradlew :app:compileDebugKotlin` and fix any
signature mismatch in `NghiTtsEngine.kt` first** (same caveat already documented for the Readium
kotlin-toolkit pin above).

### 2. Download `espeak-ng-data`

This is the shared phonemizer data used by every Piper voice (not voice-specific, bundled once
for the whole app):

1. Download
   <https://github.com/k2-fsa/sherpa-onnx/releases/download/tts-models/espeak-ng-data.tar.bz2>.
2. Extract it, and copy everything *inside* the `espeak-ng-data/` folder into
   `app/src/main/assets/espeak-ng-data/` (replacing the placeholder `README.md` there).

### 3. Import your NghiTTS voices at runtime

No further build step needed — this part is entirely in-app:

1. Settings → **TTS Models** → **Thư mục models NghiTTS** → pick a folder (anywhere on shared
   storage, via the system folder picker) containing pairs of `{name}.onnx` +
   `{name}.onnx.json` (nghitts's own distribution format) or `{name}.onnx` + `{name}.json`
   (generic Piper voices from HuggingFace).
2. Tap **Quét lại models** — the app copies each pair into private app storage, patches the
   `.onnx` copy with the ONNX metadata sherpa-onnx expects (`OnnxMetadataPatcher` — a cheap
   byte-append, never touches your original files), and generates `tokens.txt`
   (`NghiTokensWriter`). A toast reports how many voices were imported.
3. Pick a **Giọng NghiTTS mặc định** (default voice) from the now-populated list.
4. Voices then show up as a "NghiTTS" group in the reader's "Chọn giọng đọc" (Select Voice)
   dialog, same as System TTS/Edge TTS.

The app also re-scans the configured folder automatically on every launch
(`CalibreSyncApplication`), so a voice dropped into the folder while the app was closed shows up
next time you open it, without needing to tap "Quét lại" again.

## Known issues / deliberate scope cuts

- **Storage location is user-chosen, via a hybrid SAF-picker + All-Files-Access approach.** The
  original app read/wrote an arbitrary folder on shared external storage
  (`Environment.getExternalStorageDirectory()/eBooks`) using `WRITE_EXTERNAL_STORAGE`. That
  approach stopped working reliably on Android 10+ (scoped storage). A full Storage Access
  Framework rewrite (`ACTION_OPEN_DOCUMENT_TREE` + `DocumentFile` used for every read/write, no
  broad storage permission needed) is the "textbook" fix, but it touches `CalibreService`
  (`download_file`/`upload_file`/`delete_file`), `BookCrawler`'s directory-walking, and
  `OpenBookActivity` all at once, replacing every `java.io.File` call with the much more
  cumbersome `DocumentFile` API.
  <br><br>
  Instead, this app uses `ACTION_OPEN_DOCUMENT_TREE` purely as a folder-browsing *picker UI*
  (see `SettingsActivity`), then resolves the returned tree `Uri` down to a plain
  `java.io.File` path once (`StorageUtils#resolveTreeUriToFile`) and saves *that* path in
  preferences. Every existing `java.io.File`-based call site keeps working completely
  unchanged. The trade-off: this requires the `MANAGE_EXTERNAL_STORAGE` ("All files access")
  permission on Android 11+ (or classic `WRITE_EXTERNAL_STORAGE`/`READ_EXTERNAL_STORAGE` on
  10 and below) to actually read/write the resolved path, which Google Play restricts heavily
  for apps not in the "file manager" category — fine for a personal/sideloaded build, but not
  something you'd want to ship on the Play Store as-is. `resolveTreeUriToFile` only handles
  volumes with a real filesystem backing (internal storage, SD cards, USB OTG); a tree picked
  from a cloud "documents provider" (Google Drive, etc.) can't be resolved to a `File` and is
  rejected with a toast.
- **No Basic Auth UI for the OPDS Content Server.** Modern Calibre can require a
  username/password on the Content Server; `ConnectServerDialogFragment` doesn't currently
  expose fields for that. Content Server browsing without auth (or on an unauthenticated
  server) works as before.
- **UI is unrestyled.** Tabs now render as a Material `TabLayout` instead of the old ActionBar
  tabs, and the app uses a plain `Theme.MaterialComponents.DayNight.DarkActionBar` — it looks
  dated but functions. No adaptive launcher icon was created (still the original flat PNGs).
- **`SearchManager`/`searchable.xml`-based search (`BookSearchActivity`) was left as-is**,
  not migrated to a Toolbar `SearchView` — it should still work via the system search intent,
  but wasn't a focus of this pass.
- **`canSupportLpathChanges`/`wantsSendOkToSendbook`** (optional newer capability flags Calibre
  supports) were **not** added to the `GET_INITIALIZATION_INFO` reply — the client still uses
  the legacy compatibility mode, which Calibre's server falls back to automatically. Protocol
  still works, just not the newest optional handshake.
- **In-app reader toolbar ("chrome") is a plugin-style layer, not fully wired up yet.** All three
  readers (EPUB/PDF/CBZ) now share one floating toolbar
  (`net.mrphan.calibre.reader.chrome.ReaderChromeOverlay`) driven by a small registry of
  `ReaderAction`s (`ReaderActionRegistry`) — tap the middle of the screen to show/hide it. Real,
  working buttons: Quit/Đóng, Trở lại/Tiếp theo (back/forward), Lật tới... (goto page/location),
  Cỡ chữ (EPUB font size), Dãn hết màn hình (fullscreen), Nạp lại (reload), Mở sách (back to
  library). Đọc cho nghe / Hiệu đính / Print are intentional "coming soon" stubs; Tìm kiếm /
  Đánh dấu trang / Tinh chỉnh / Inspector / Thống kê currently report "không hỗ trợ" since there's
  no real feature behind them yet on any format. See `CHANGELOG_MIGRATION.md`'s "in-app reader
  gets a real toolbar" entry for the full architecture writeup and the `TODO` comments in
  `EpubReaderActivity.kt`/`PdfReaderActivity.java`/`CbzReaderActivity.java` for what each stub
  would need to become real.
- **Edge TTS / NghiTTS engines added but not build-tested.** Same root cause as the bullet
  above — no Android SDK in this sandbox. `EdgeTtsEngine`/`EdgeTtsClient` only depend on OkHttp
  + org.json (both already proven dependencies elsewhere in this project), so risk there is low;
  `NghiTtsEngine`'s sherpa-onnx calls are the piece most likely to need a signature fix after you
  add the real `.aar` — see "TTS Models / NghiTTS setup" above.
- **Not build-tested in this environment** — see the build-status section above. Please report
  back the first compiler error(s) if any, with the full `./gradlew assembleDebug` log.
